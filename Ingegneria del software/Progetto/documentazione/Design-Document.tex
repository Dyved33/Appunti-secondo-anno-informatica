\section{Contesto, obiettivi e non obiettivi}
% ============================================================

GiaLoSai \`{e} un sistema client--server per la gestione logistica interna di un'azienda: prodotti, categorie, giacenze, ordini di entrata e uscita, DDT, fatture, note di credito, resi e utenti con ruoli differenziati. Il backend \`{e} scritto in Go, espone API REST (Representational State Transfer) e persiste su MySQL 8 tramite Docker Compose. Il client \`{e} una TUI (Text-based User Interface) scritta in Go con il framework Bubble Tea.

\gialosaiNote{Il progetto segue le best practice dei moderni strumenti CLI: come \texttt{docker} e \texttt{kubectl}, GiaLoSai separa il client leggero (TUI) dal backend, comunicando tramite API REST con autenticazione JWT (JSON Web Token). Il pattern \`{e} lo stesso utilizzato da \texttt{gh} (GitHub CLI) e \texttt{aws} CLI.}

\subsection{Obiettivi}
\begin{itemize}
    \item Gestire l'intero ciclo della merce: dall'anagrafica prodotti fino a DDT, fatture, note di credito e resi.
    \item Fornire tre ruoli (magazziniere, contabile, admin) con funzionalità distinte.
    \item Garantire atomicità delle operazioni multi-entità tramite transazioni MySQL.
    \item Raggiungere un livello documentale e testuale adeguato a un progetto universitario.
\end{itemize}

\subsection{Non obiettivi}
\begin{itemize}
    \item Canale e-commerce o raccolta ordini dal cliente finale.
    \item Generazione materiale di PDF o CSV: i percorsi sono registrati nei modelli ma non esiste un generatore.
    \item Microservizi, orchestratori (Kubernetes) o distribuzione cloud.
    \item Autenticazione OAuth2/OIDC o federazione SSO.
\end{itemize}

\section{Proposta architetturale}
% ============================================================

Il sistema combina gli stili \emph{client--server}, \emph{layered} e \emph{repository}. Il client TUI in Go è un processo separato dal backend e comunica con esso in HTTP/JSON. Il backend Go centralizza le regole applicative e accede a un repository dati MySQL condiviso. Non è un'architettura a microservizi: i package del server sono moduli di un singolo processo.

\begin{verbatim}
+--------------+      HTTP/JSON       +----------------------+
|  Client TUI  | -------------------- |   Backend REST Go    |
|  Bubble Tea  |  Authorization:      |   chi router         |
|  Lipgloss    |  Bearer <JWT>        |   +-- middleware      |
+--------------+                      |      +-- controller   |
                                      |         +-- service   |
                                      |            +-- repo   |
                                      +-----------+-----------+
                                                  |
                                           +------+------+
                                           |  MySQL 8    |
                                           |  (Docker)   |
                                           +-------------+
\end{verbatim}

\gialosaiNote{L'architettura segue lo stesso pattern di \texttt{docker}: un binario singolo che espone API HTTP, con un client TUI separato che interagisce con esso. Il modello ``backend + client separati'' è lo stesso utilizzato da \texttt{portainer}, \texttt{k9s} e \texttt{lazygit}.}

La soluzione risponde a tre esigenze: separare l'esperienza utente dalla logica applicativa, concentrare la persistenza in un punto controllato e mantenere le regole di dominio testabili senza richiedere sempre risorse esterne.

\subsection{Pattern e principi effettivamente applicati}

Il modello è un'architettura a layer, non un MVC classico: i controller sono adattatori HTTP e la view è nel processo client separato.

\begin{itemize}
    \item \textbf{Repository pattern}: ogni package di dominio ha un repository che incapsula l'accesso SQL. I service dipendono da interfacce ristrette (non dalle implementazioni concrete), coerentemente con \emph{Dependency Inversion} e \emph{Interface Segregation}. Ciò consente l'uso di mock (\texttt{go-sqlmock}) nei test. Questo pattern è lo stesso utilizzato da \texttt{database/sql} in Go e da progetti come \texttt{github.com/jmoiron/sqlx}.
    \item \textbf{DTO (Data Transfer Object)}: le strutture di trasporto HTTP sono separate dalle entità del dominio. Ogni package ha i propri DTO (\texttt{AuthDTO}, \texttt{UserDto}, \texttt{ProductDto}, \texttt{OrderDto}, \texttt{CategoryDto}). Il pattern è lo stesso adottato da \texttt{docker} API e \texttt{kubernetes} API.
    \item \textbf{Transaction-in-context}: \texttt{TransactionHelper.WithinTransaction} inserisce una transazione SQL nel \texttt{context.Context}; i repository la estraggono con \texttt{GetExecutor}. Il pattern è trasparente ai service e supporta nesting. Simile al pattern utilizzato da \texttt{sqlx} e \texttt{gorm}.
    \item \textbf{Model--View--Update (MVU)}: il client TUI applica il pattern Elm su ogni pagina. Ogni package pagina espone \texttt{Init()}, \texttt{Update()} e \texttt{View()} come interfaccia Bubble Tea. Lo stesso pattern è utilizzato da \texttt{lazygit}, \texttt{k9s}, \texttt{btop} e \texttt{htop}.
    \item \textbf{Sentinel errors}: \texttt{domain/errors.go} definisce errori sentinella (\texttt{ErrGiacenzaInsufficient}, \texttt{ErrAccountBloccato}, \texttt{ErrCredenzaliErrate}, ecc.) per il controllo degli flussi di errore nei service. Pattern standard in Go, utilizzato anche da \texttt{net/http} e \texttt{io}.
\end{itemize}

Non vengono dichiarati Strategy, Factory, Observer o Adapter come pattern di progetto, poiché il codice non contiene collaboratori intercambiabili o punti di estensione che ne giustifichino l'attribuzione.

\subsection{Transazioni}

\texttt{TransactionHelper} (\texttt{domain/db.go}) apre una transazione e la propaga nel \texttt{context.Context}. I repository estraggono l'executor con \texttt{GetExecutor(ctx, r.DB)}, che restituisce la transazione se presente nel contesto, altrimenti la connessione diretta. Questo confine atomico protegge:

\begin{itemize}
    \item \textbf{Ordini di entrata}: inserimento righe e incremento giacenze nello stesso \texttt{BEGIN/COMMIT}.
    \item \textbf{Ordini di uscita}: verifica disponibilità, decremento giacenze e registrazione ordine. Un errore di giacenza insufficiente causa \texttt{ROLLBACK}.
    \item \textbf{Login}: read-modify-write atomico dei tentativi falliti e del flag blocco.
    \item \textbf{Resi}: aggiornamento stato e ripristino/reintegro giacenza in transazione.
\end{itemize}

\gialosaiNote{Il pattern di transazione in contesto è lo stesso utilizzato da \texttt{database/sql} di Go e da ORM come \texttt{gorm}. La propagazione via \texttt{context.Context} è la best practice raccomandata dal team di Go per la gestione delle transazioni.}

\subsection{Autenticazione}

Il flusso di autenticazione è il seguente:

\begin{enumerate}
    \item Il client invia \texttt{POST /api/v1/login} con username e password.
    \item Il server verifica le credenziali con \texttt{bcrypt.CompareHashAndPassword}.
    \item Se valide, genera un JWT HS256 (\texttt{golang-jwt/jwt/v5}) con claim \texttt{user\_id}, \texttt{username}, \texttt{role} e scadenza 24h.
    \item Il token viene hashato con SHA-256 e salvato nella tabella \texttt{Sessioni} (mai in chiaro).
    \item Il client conserva il JWT e lo invia come \texttt{Authorization: Bearer <token>} a ogni richiesta protetta.
    \item Il middleware verifica: (a) firma JWT e scadenza, (b) presenza della sessione hashata nel DB, (c) inietta \texttt{userID} nel contesto.
\end{enumerate}

\gialosaiNote{L'autenticazione JWT con whitelist è lo stesso approccio utilizzato da \texttt{docker} (con token di accesso) e \texttt{kubectl} (con certificati e token). Il pattern di hash SHA-256 del token è una best practice per evitare che token compromessi siano riutilizzabili.}

Dopo tre tentativi di accesso falliti consecutivi, l'account viene bloccato (\texttt{RF-02}). L'account con username \texttt{admin} è esente dal blocco. Il ripristino avviene solo tramite un altro admin che sblocca l'account e imposta una nuova password.

\section{Architettura client TUI}
% ============================================================

Il client è una TUI Go basata su Bubble Tea v2 (architettura Model--View--Update) con Lipgloss v2 per lo stile. Il modello principale \texttt{mainLayout} (\texttt{client/ui/app/}) ospita tutti i sub-model e gestisce la navigazione.

\gialosaiNote{Bubble Tea è il framework TUI più utilizzato nell'ecosistema Go, con progetti come \texttt{lazygit} (25k+ stelle), \texttt{glow} (rendering markdown), \texttt{soft-serve} (server Git TUI) e \texttt{charm} (la stessa azienda che lo sviluppa). Il pattern MVU è lo stesso di \texttt{Elm} e \texttt{Redux}, reso popolare da applicazioni web reattive.}

\subsection{Navigazione}

La navigazione è controllata da un enum \texttt{paginaAttiva} definito con \texttt{iota}:

\begin{verbatim}
const (
    LOGIN     paginaAttiva = iota  // 0
    MAGMENU                         // 1 - Menu magazzino
    CONTMENU                        // 2 - Menu contabilità
    ADMINMENU                       // 3 - Menu admin
)
\end{verbatim}

Ogni menu espone le proprie sottopagine. Il metodo \texttt{Update()} del modello principale esegue uno \texttt{switch} sul valore corrente di \texttt{paginaAttiva} per instradare i messaggi alla sottopagina attiva. La navigazione avviene tramite scorciatoie da tastiera (\texttt{ctrl+F1}, \texttt{ctrl+F2}, ...) e \texttt{ctrl+L} per il logout.

\gialosaiNote{Il sistema di navigazione a enum è lo stesso utilizzato da \texttt{lazygit}, \texttt{k9s} e \texttt{btop}. La navigazione a scorciatoie da tastiera è una best practice per TUI, garantendo efficienza e accessibilità.}

\section{Flussi dati principali}
% ============================================================

\subsection{Login}
\begin{enumerate}
    \item Client invia \texttt{POST /api/v1/login} con \texttt\{"username", "password"\}.
    \item \texttt{AuthService\_Login} estrae l'utente dal DB, verifica blocco e password bcrypt.
    \item Se ok: genera JWT (HS256, scadenza 24h), hash SHA-256 del token, salva in \texttt{Sessioni}, resetta tentativi falliti.
    \item Se password errata: incrementa tentativi; se $\geq 3$ imposta \texttt{bloccato = true}.
    \item Risposta: \texttt\{"token": "...", "role": "magazziniere"\}.
\end{enumerate}

\subsection{Ordine di uscita con generazione DDT}
\begin{enumerate}
    \item Magazziniere compila l'ordine nella TUI e invia \texttt{POST /api/v1/orders/crea-uscita}.
    \item \texttt{OrderService} apre una transazione con \texttt{WithinTransaction}.
    \item Per ogni riga: verifica che \texttt{quantita} $\leq$ giacenza disponibile. Se insufficiente, restituisce \texttt{GiacenzaInsufficienteError} e la transazione esegue \texttt{ROLLBACK}.
    \item Se tutte le quantità sono sufficienti: decrementa le giacenze, registra l'ordine con stato \texttt{confermato}, commit.
    \item Il magazziniere genera il DDT con \texttt{POST /api/v1/orders/\{id\}/create-ddt}: il service assegna una numerazione annuale progressiva, crea il record DDT e aggiorna lo stato dell'ordine a \texttt{evaso}.
\end{enumerate}

\subsection{Gestione resi}
\begin{enumerate}
    \item Il reso viene creato con stato \texttt{da\_verificare}.
    \item alla verifica (\texttt{PUT /api/v1/orders/update-resi}), lo stato passa a \texttt{accettato} (con ripristino giacenza) o \texttt{rifiutato} (con riduzione giacenza). Entrambe le operazioni sono transazionali.
\end{enumerate}

\section{Alternative considerate}
% ============================================================

Le alternative progettuali principali sono state valutate e scartate per i motivi seguenti.

\textbf{GUI o applicazione web al posto della TUI.} Un'interfaccia grafica o web avrebbe richiesto più lavoro di configurazione e distribuzione senza aggiungere capacità richieste dai vincoli del progetto; la TUI resta eseguibile da terminale e separata dal backend tramite API HTTP. Il successo di TUI come \texttt{htop}, \texttt{lazygit}, \texttt{k9s} e \texttt{btop} dimostra che un'interfaccia testuale ben progettata può essere più efficiente di una GUI per operazioni amministrative.

\textbf{SQLite al posto di MySQL.} Un database embedded semplifica l'avvio locale, ma il sistema richiede un repository condiviso multiutente con vincoli relazionali e operazioni multi-entità; MySQL 8, gestito con Docker Compose, centralizza dati e regole in un punto controllato.

\textbf{Architettura a microservizi.} La separazione in servizi indipendenti avrebbe introdotto complessità di comunicazione e di deploy non giustificata dalle dimensioni del sistema; si è preferito un processo monolitico a layer con confini espliciti tra router, controller, service, repository e domain.

\textbf{DAO generico al posto del Repository pattern.} Un accesso ai dati di tipo DAO sarebbe stato più generico ma avrebbe accoppiato i service al dialetto SQL; i repository, associati alle aree di dominio, espongono interfacce ristrette coerenti con Dependency Inversion e facilitano i test con mock.

\textbf{ORM (GORM) al posto di \texttt{database/sql}.} Un ORM avrebbe ridotto il boilerplate delle query ma avrebbe introdotto un livello di astrazione opaco, harder da controllare per operazioni transazionali complesse e meno trasparente nel debugging.

\textbf{Sessioni classiche (cookie) al posto di JWT.} Le sessioni con cookie non sono adatte a un client TUI che non ha un browser; JWT con whitelist nel DB consente logout effettivo e controllo server-side della sessione. Il pattern è lo stesso utilizzato da \texttt{docker} (con token di accesso) e \texttt{kubectl} (con certificati e token).

% ============================================================
\section{Conseguenze e limiti}
% ============================================================

La separazione aumenta coesione e testabilità, ma introduce dipendenza dalla rete locale e dalla disponibilità di MySQL. Il repository centralizzato semplifica la consistenza dei dati, ma costituisce un punto operativo comune da gestire con backup e monitoraggio.

L'integrazione finale (v2.0.0) ha allineato client e server: le principali funzionalità sono esposte via API e raggiungibili dalla navigazione TUI. I limiti residui riguardano:

\begin{itemize}
    \item \textbf{Autorizzazione RBAC}: il ruolo è presente nel token JWT ma non è ancora verificato dal router sulle singole rotte. Qualsiasi utente autenticato può accedere a qualunque endpoint protetto.
    \item \textbf{Generazione documenti}: i percorsi PDF sono registrati nei modelli (\texttt{DDT.PathPDF}, \texttt{Fattura.PathPDF}) ma il codice non contiene un generatore di PDF o CSV.
    \item \textbf{Bootstrap primo utente}: l'ambiente Compose fornisce utenti di prueba via seed script; avviando il server sull'host senza Compose, il primo utente deve essere creato manualmente nel database con password bcrypt.
    \item \textbf{Navigazione TUI}: alcune viste amministrative secondarie non sono ancora collegate alla navigazione principale.
\end{itemize}
